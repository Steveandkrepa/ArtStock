# ArtAssist · 美术生的工具箱

一个 iPad 优先的原生 App，给**一个美术生**用。三件事：

| 模块 | 干什么 |
|---|---|
| **颜料盒** | 7×6 一整盒的余量管理：哪几格该补、抽屉里的补充装够不够、该不该买 |
| **保湿计时** | 颜料多久会干，什么时候喷水；切到别的 App 也能看见（画中画） |
| **教材** | 搜平台上的美术教材，下载到本地离线看；**用 Apple Pencil 直接在页面上批注** |

配色/色值取自你这盒颜料的**厂家色卡实测值**，不是猜的。
联网只发生在两处，都是你自己触发的：取当地天气、搜/下教材。

> 原名「材料余量 / ArtStock」。因为加入了教材阅读（而且是重头戏），
> 改名为 **ArtAssist**。Bundle ID 保持 `com.yuanjunhao.artstock` 不变 ——
> 这样升级安装不会丢数据。

## 1. 它到底是什么（以及它不是什么）

**是**：个人美术生的一盒颜料管理工具。打开就是 7×6 网格，点一格改余量，
缺的时候告诉你「抽屉里还有没有」「要不要买」「买几件」。

**不是**：仓库管理软件。

> ⚠️ 这一条是踩过坑写下来的。第一版做成了带供应商、单价、库存价值、
> A4 标签打印、CSV 导出、操作人、三栏导航的**画室库房系统** ——
> 完全偏离了受众。如果你在别处看到这类字段（`supplier` / `unitPrice` /
> `LabelRenderer` / `InventoryCSVExporter`），那是被淘汰的版本，
> 旧版完整备份在 `.backup-v1/ArtStock-v1.tar.gz`。

## 2. 核心概念：两层库存

这是整个 App 的骨架。

| 层 | 是什么 | 存在哪 |
|---|---|---|
| **存量** | 盒子里 42 格，每格还剩多少颜料 | `PaletteWell.level`（五档目测） |
| **库存** | 抽屉里的补充装，还有多少 | `RefillStock` |

补充装有**两种**，消耗方式完全不同：

| 类型 | 消耗方式 | 能不能拆开用 |
|---|---|---|
| **挤出补充装** | 软管装，挤进格子。**一支能补好几格** | 能 —— 开封后用不完，剩余量单独记 |
| **直接替换装** | 固体块，一格换一个 | 不能 —— 一格一个，用完即尽 |

### 统一度量：「还能补几格」

两种补充装要和「盒子里有几格空了」对上，必须换算到同一个单位：

```
挤出补充装：未开封支数 × 每支可补格数 + 已开封那支的剩余量
直接替换装：个数 × 1
```

三个判据全部建立在这个量上：

| 情况 | 结论 |
|---|---|
| 还能补 ≥ 需要补 | **抽屉里有货，别买** |
| 还能补 < 需要补 | **有缺口，该买 —— 且只买缺口** |
| 还能补 ≫ 长期用量 | **已经过多，别再买了** |

> 「已开封那支的剩余量」是"不过多"的关键。挤出补充装一旦开封就用不满整支：
> 当成整支可用会高估库存 → 重复购买；直接丢弃会低估 → 漏买。

这套算术在 `Services/RefillMath.swift` 里，是**纯函数**，由
`scripts/run-math-tests.sh` 的 **73 个用例**覆盖 —— 因为"不缺也不过多"
这句承诺实际上就落在三个算术上。

## 3. 界面

侧边栏四个分区，主区域是当前分区的全部内容。

### 颜料盒（主界面）

```
┌──────────────────────────────────────┐
│  ⚠️ 4 格该补了                        │
│     其中 1 格没有补充装 · 建议买 1 个颜色 │
├──────────────────────────────────────┤
│  A1  A2  A3  A4  A5  A6              │  ← 每格一个色块
│  B1  B2  B3  B4  B5  B6                 │     底部细条＝余量
│  C1  C2  C3  C4  C5  C6                 │     右上角❗＝该补
│  ...                                  │     左上角＝位置编号
└──────────────────────────────────────┘
```

- 格子的主角是**颜色本身**，文字只留一个位置编号
- 余量用底部细条，**不满才画** —— 42 格全画会变成噪声
- 点任意一格 → 弹层：五档余量大按钮 + 补充 + 换颜色
- **长按拖动可以换位置**：把一格拖到另一格上，两格的内容（颜色 + 余量 + 上次补充时间 + 备注）整体对调

> 关于拖动换位的语义：交换的是**格子里的东西**，不是格子本身 ——
> 格子代表实物位置，位置不会动。余量必须跟着颜色一起走，
> 否则「满的群青」和「快没了的湖蓝」对调后会变成「满的湖蓝」，跟实物对不上。

### 库存与采购

先给结论（该买什么 / 什么都不用买），再列要行动的颜色，最后是"偏多"的提醒。

### 其他耗材

纸、笔、橡皮、胶带。刻意做得很轻 —— 一行一个，点一下改数量。

### 设置

盒子概览、数据量、清空数据、关于。就这些。

## 3.5 保湿计时（颜料多久会干）

调好一盘颜色要离开一段时间时开个计时，到点本地提醒你该喷水了。

### 湿度从哪来

**用天气 API，不是解析天气预报网站。** 这是实测过的：

| 方案 | 结果 |
|---|---|
| Open-Meteo 公开接口 | ✅ 干净的 JSON：湿度 66% / 温度 24.9℃，免费、无密钥 |
| 中国天气网 | HTTP 200、85 KB HTML，**原始内容里找不到任何湿度数据** |
| 中国气象局 | HTTP 200、76 KB HTML，**同样找不到** |

现代天气站的湿度是 **JS 在前端渲染**的，iOS App 里没有浏览器引擎，
抓回来的只是一个空壳。所以「解析天气网站」这条路走不通，
而 API 就是它想要的东西，还更干净。

### ⚠️ 但室外湿度不等于画室湿度

空调、暖气、加湿器、门窗开关、旁边一个洗笔筒，能让室内外差出二三十个百分点。
所以**开始计时时会让你确认一次，湿度可以直接拖**——那不是装饰性的设置项，
是这个功能准确性的关键一步。

### 预测模型

```
饱和水汽压  es(T) = 0.6108 · exp(17.27·T / (T + 237.3))   [kPa]   ← Magnus 公式
水汽压差    VPD   = es(T) · (1 − RH/100)                [kPa]   ← 蒸发/结皮的真实驱动力
结皮时间    t     = K / VPD                             [h]
补水时刻    t × 0.5                                     ← 结皮不可逆，要提前动手
```

VPD 是农业与园艺里标准的"干燥驱动力"指标。**但 K 必须由你实测校准**——
它由颜料体系、膜厚、容器密闭程度共同决定，App 一个都拿不到，
所以默认值只是让功能开箱可用的起点猜测，不是测量结果。

**校准只要一分钟**：计时中点「其实已经干了」，App 用真实时长反推你的 K 并保存。
这比任何公式都准。反推时要把容器倍数和补水比例都除回去——
早期版本漏掉了这一步，导致「实测 10 小时」校准后预测只有 5 小时，
正好差一倍，是被测试用例抓出来的。

### 提醒走本地通知

免费 Apple ID 签不出 `aps-environment`，所以远程推送用不了。
但**本地通知不需要任何 entitlement**，而且对本功能本来就够——
补水依据在开始计时那一刻就全部拿到了。会排两条：
提前 10 分钟预警 + 到点正式提醒（带建议喷雾下数）。

### 还需要你做一件事

**「喷一下能维持多久」要自己量一次**（设置 → 保湿计时）。
不标定的话，提醒里只会给时间、不会给「喷几下」。

## 3.6 补充装库存与采购

「库存与采购」这个分区管的是**抽屉里的补充装**，两种分开记：

| 类型 | 消耗方式 | 记录什么 |
|---|---|---|
| **挤出补充装** | 软管装，挤进格子。一支能补好几格 | 还有几支 + 每支能补几格 + **已开封那支还剩几格** |
| **直接替换装** | 预装颜料块，整格换掉 | 还有几个（一件补一格，不用换算） |

### 怎么用

侧边栏 →「库存与采购」。默认显示**全部颜色**，每一行直接列出两种补充装各有多少：

```
群青                     [该补]
该补 2 格 · 抽屉里有货
🧴 挤出装 1 支 + 剩 1    ▣ 替换装 0 个
```

点任意一行进入编辑：两种补充装各有多少、每支能补几格、已开封剩几格。
右上角 `+` 可以给**任意颜色**登记补充装（不要求它已经装进盒子）。

### 页面顶部的结论

打开这一页，最上面直接给答案，看完就能关掉：

> **该补货了** · 建议买 2 个颜色、共 3 件
> 群青　缺 2 格，挤出装每件补 3 格　→　**买 1 支**

三个判据见 [第 2 节](#2-核心概念两层库存)，算术在 `RefillMath.swift`，**73 个用例**守着。

> 🐞 **这里修过一个"功能明明写了却看不见"的 bug**：
> 默认筛选原本是「要处理的」，只显示"该买/该补"的颜色。
> 而刚载入 42 色预设时所有颜色都还没装进盒子（状态是"未装盒"），
> 于是**列表全空**、界面显示"没有要处理的颜色"——
> 用户合理地以为补充装管理这个功能根本不存在。
>
> 默认筛选已改为「全部颜色」，并补了 `+` 登记入口与空状态指引。

## 3.7 色卡：42 色预设置与"颜色到底该是什么色"

**首次打开就自动装满一整盒**（42 格 × 42 色），不用去菜单里找。
只有在「颜色库为空」且「一格颜色都没分配」时才会自动装；
你只要动过任何一格，这条路就永久关闭（`AppStorage` 标记），绝不会在你没注意的时候把颜色冲掉。

顺序**就是**这盒颜料的排布顺序（从左到右、从上到下），
第 1 个「钛白」进 A1、第 42 个「黑色」进最后一格。

```
钛白   那坡里黄 柠檬黄  嫩黄   淡黄   中黄
土黄   桔黄    桔红   朱红   大红   深红
赭石   熟褐    豆沙红  肉色   米驼   蔷薇
紫丁香 淡紫    玫瑰红  香水百合 青苹果 黄绿
淡绿   草绿    橄榄绿  墨绿   起司   马尔代夫
春日青 晴朗蓝  浅蟹灰  紫罗兰 群青   浅灰蓝
青竹蓝 天蓝    湖蓝   钴蓝   普蓝   黑色
```

### ⚠️ 踩过的坑：我按色名"套"过色值，套错了

真实的错误反馈：

> 「像马尔代夫就根本不像啊颜色，是个绿色的，显示个蓝色的」

这条反馈是对的，而且根因比一个颜色更严重 ——
**颜料领域没有 RGB 的国际标准**，当初那 42 个色值是我按色名硬套出来的：
「马尔代夫」套了 W3C CSS 的 `turquoise`（`#40E0D0`），显示出来当然是蓝的。

| 标准 | 它规定什么 | 能不能给"马尔代夫"一个色值 |
|---|---|---|
| **Colour Index（C.I.）** | **化学成分**（PW6 = 钛白、PB29 = 群青） | ❌ 不规定 RGB |
| **W3C CSS Color Module** | 148 个具名颜色 | ❌ 跟品牌自创色名毫无对应关系 |
| 各厂家的产品色卡 | 该品牌该型号的实际色相 | ✅ **这才是唯一来源** |

所以"查一个更权威的表"这条路根本不存在。**正解是从实物/厂家色卡上采。**

### 现在的色值：从厂家色卡逐格实测

用户提供了这盒颜料的官方 42 色色卡图，42 个色值是把每一格色块**逐格采样**得到的。
采集脚本（`Tests/` 那套之外的一次性分析）做了四件事，每件都是为了不采错：

1. **先测真实格子边界** —— 卡片有内白边、格子之间有白缝，
   所以不能把卡片范围除以 7 和 6（第一版就是这么错的，采出了整体偏移的值）
2. **每格只取上半部分** —— 下半是半透明的名字色带，采进去会把颜色压暗
3. **校验取色区间敏感性** —— 换一个区间最大通道差只有 `2/255`，说明色块基本是平的
4. **校验锚点** —— 钛白 `#FEFEFE`、黑色 `#030304`、马尔代夫是**绿的**、群青是深蓝

结果里几个值得看的：

| 颜色 | 旧（猜的） | 现在（实测） |
|---|---|---|
| 马尔代夫 | `#40E0D0` 蓝 ✗ | `#AED47F` 绿 ✓ |
| 群青 | `#23319E` | `#232E62` 深得多 |
| 熟褐 | `#8A3324` | `#502E17` 深得多 |
| 香水百合 | `#F8C8DC` 粉 ✗ | `#B0C925` **黄绿** |
| 起司 | `#F0C420` 橙黄 | `#D8DD5D` 黄绿 |
| 玫瑰红 | `#C21E56` | `#BB1A5C` |

**升级后会自动校正**：启动时发现本地色卡版本落后就自动刷一次，不用自己找菜单。
三条安全边界：取色校准过的、改过名的、你自己建的颜色**都不会被覆盖**。

### 还能更准：取色校准

色卡是屏幕上的图，跟画室灯光下的实物观感仍有差距，同批不同批也有微差。
所以「颜色库」里还有**取色校准**：把打开的颜料盒对着相机，
屏幕上实时显示即将写进每一格的 42 个色块，拿它跟实物比一下，确认了再保存。
可以拖动/双指缩放采样框去对准，也可以进「微调」逐项调。

采过的颜色会打「已校准」标记，之后**任何操作都不会覆盖它**。

### 测试

预设色卡有 **33 个用例**守着（`scripts/run-preset-tests.sh`）：
数量正好 42、色值合法、名称与色号与色值都不重复、顺序逐个比对、
**42 个色值必须全部来自实测**（不许再往回塞猜的值）、
明度锚点（白够白黑够黑）、**色相锚点**（绿是绿蓝是蓝红是红黄是黄褐是暗棕）、
色轮六区覆盖、8 个 C.I. 标准号逐个钉死。

## 3.8 首次启动的权限引导

第一次打开会有一个三页的引导，最后一页点「允许并开始使用」会**依次申请相机和通知权限** ——
跟其他 App 一样，权限弹窗就该在首次打开时出现。

引导页会先说明**为什么**需要每个权限，再弹系统弹窗。系统弹窗自己只有一句话，
用户不知道用途就容易点拒绝，而拒绝之后要再去设置里开就很麻烦。

「设置 → 运行环境」里能看到两个权限的当前状态，还有一个「申请还没问过的权限」按钮
（系统弹窗只对"从没问过"的权限出现；已经拒绝过的只能去系统设置里改，App 无能为力）。

> 🐞 **这里修过一个会导致相机彻底不可用的 bug**，记录在此避免重犯：
>
> 早先版本把扫码视图写成 `if 已授权 { 相机视图 } else { 降级界面 }`，
> 而**申请权限的代码写在那个相机视图里**。于是形成死循环：
>
> ```
> 未授权 → 不创建相机视图 → 不申请 → 永远未授权
> ```
>
> 后果是**相机在任何环境下都用不了**（不只是 LiveContainer），
> 而且表面现象是"没有可用摄像头"，很容易被误判成环境问题。
>
> 修法：相机视图**始终挂载**，未授权时把降级界面**盖在上面**，而不是替换它。
> 代码里已加注释标明不要改回条件挂载。

## 3.9 在 LiveContainer 里运行

可以正常运行。LiveContainer 的权限机制有一条要说清楚（**我一开始理解错了，这里更正**）：

> LiveContainer README「Limitations」原文：
> - Entitlements from the guest app are not applied to the host app.
> - **App Permissions are globally applied.**

「全局」的意思是**授权记录挂在 LiveContainer 本体上**，不是每个 guest App 各有一份。
但它**不影响申请这个动作**：

- 调用 `AVCaptureDevice.requestAccess` → 弹窗会出来（归属于 LiveContainer）
- 你同意 → LiveContainer 获得相机权限 → **所有 guest App 都能用**
- 所以你看到"别的 App 打开就申请好了权限"，是正常的，本 App 也一样

真正卡住相机的是前面那个 bug（视图条件挂载导致申请根本没发出去），**已经修好了**。

### 通知需要开一个开关

这一条是 LiveContainer 官方文档明确写的，与本 App 无关：

> Some apps may experience issues with **not being able to apply for notification permission**
> in LiveContainer. To resolve this, enable **`Fix Local Notifications`** in the app-specific settings.

```
长按 LiveContainer 里的这个 App → 设置 → 打开 Fix Local Notifications
```

不打开的话，保湿计时的到点提醒排不出来（`UNUserNotificationCenter.add` 会静默失败）。

### 如果相机仍然不工作

极少数情况下 LiveContainer 本体的相机权限被拒过，这时：

```
系统「设置」 → LiveContainer → 相机 → 打开
```

找不到「相机」这一项的话，先在 LiveContainer 里跑一次别的用相机的 App 触发一次授权。

**兜底**：相机不可用时，「手动输入编号」是完整方案而不是残废版 ——
它走的是**和扫码完全相同的解析管线**，粘贴一段 JSON 也能直接结构化入库。

## 3.10 扫码功能踩过的两个坑（都在同类问题上犯过）

这两个 bug 有共同特征：**都不报错，只表现为"功能不对"**，
所以现场看着特别像环境问题 —— 也因此更容易被误判。

### 坑一：相机权限死循环 —— 相机完全用不了

```swift
// ❌ 错误写法
if controller.authorization == .authorized {
    QRScannerView(...)      // 申请权限的代码写在这个视图里
} else {
    cameraFallback
}
```

未授权 → 不创建相机视图 → 申请根本没发出去 → 永远未授权。

后果是**在任何环境下相机都不可用**，但现场表现是"没有可用摄像头"，
看起来像设备或环境问题。

✅ **修法**：相机视图**始终挂载**，未授权时把降级界面**盖在上面**。
代码里已加注释标明不要改回条件挂载。

### 坑二：相机方向不对 —— 手写旋转映射

早先版本**刻意没用**官方的 `RotationCoordinator`，自己按
`windowScene.interfaceOrientation` 硬映射角度（portrait→90、landscapeLeft→0 …）。
那个映射只考虑了界面方向，漏掉了两个同样决定角度的因素：

- **摄像头位置** —— 前置传感器是镜像的，角度与后置不同
- **iPad 上窗口不一定跟着设备转** —— Stage Manager / 分屏下
  `interfaceOrientation` 和真实握持方向可以完全不一致

手写映射要覆盖这些组合很容易漏，而且错了**不报错、只表现为画面歪掉**。

✅ **修法**：改用 `AVCaptureDevice.RotationCoordinator`（iOS 17.0+，
正好是本工程的最低版本）。它同时给出**预览**和**采集**各自该用的角度，
还带水平线对齐。两个 connection 都要设 ——
只设预览的后果是"画面是正的，但高亮框歪着"。

### 一条通用教训

这两个 bug 都发生在"我为了简单而绕开官方 API"的地方。
`RotationCoordinator` 就是 Apple 为这件事做的，绕开它自己算，
省下的代码量远不值得那些漏掉的组合。

## 3.11 保湿计时的画中画

计时中，会话卡片上有一个「在画中画里显示」。点开之后，
**还剩多久、该喷几下**会变成一个悬浮小窗，一直浮在别的 App 上面 ——
你在 Procreate 里画画，不切回来也能看见。

窗口里只有三层信息，因为 PiP 窗口在 iPad 上可能只有指甲盖大、还是用眼角余光看的：

```
┌──────────────────────────────┐
│ 群青 · 密闭调色盒      [该喷了] │
│                              │
│          2:14                │   ← 最大最粗，唯一的主角
│                              │
│       🧴 喷 3 下              │
└──────────────────────────────┘
```

背景色随紧急程度变化（青绿 → 琥珀 → 橙红 → 深红），
**不用读数字，扫一眼颜色就知道该不该动手**。

### 为什么只能用画中画

PiP 本来是给视频用的。要让**任意内容**（这里是几个数字）进 PiP，
唯一的路子是 `AVPictureInPictureController.ContentSource(
sampleBufferDisplayLayer:playbackDelegate:)`（iOS 15+）——
自己把画面渲染成 `CMSampleBuffer` 喂给 `AVSampleBufferDisplayLayer`。

所以代码里有一条**手动渲染管线**：

```
SwiftUI 视图 ──ImageRenderer──▶ UIImage ──▶ CVPixelBuffer ──▶ CMSampleBuffer ──▶ displayLayer
```

另一个看着更合适的技术 —— **Live Activity —— 在 iPad 上不可用**
（那是 iPhone 锁屏与灵动岛的东西）。所以对 iPad 来说，
PiP 是唯一能做到"悬浮常驻"的手段。

### 免费 Apple ID 下能用吗

**能。** 它需要 `Info.plist` 里的 `UIBackgroundModes = [audio]`，
那是 plist 键、**不是 entitlement**，SideStore 自签不受影响。
本工程的 `Resources/Info.plist` 已声明。

LiveContainer 的 Info.plist 里**也已经包含 `audio`**（顺带还有一堆别的），
所以在 LiveContainer 里这条路也是通的。

### ⚠️ 没能实测的部分

这个环境没有真机、也没有模拟器 runtime，所以两件事**我无法验证**：

1. **PiP 窗口在 App 完全切到后台后能否持续存活**
2. **在 LiveContainer 里的实际表现**

代码按 Apple 的要求做了（激活音频会话 + `audio` 后台模式），
但这是整个功能里我最没把握的一段 —— 见 `WetnessPiPController.activateAudioSession()`
里的注释。如果真机上 PiP 一进后台就消失，问题八成在那里
（常见做法是循环播一段静音音频来维持后台存活，但那是绕过系统策略的 hack，
我不想在没实测的情况下先写进去）。

如果出现这种情况，告诉我，我按现象调。

## 3.12 认字：条码认不出颜色，字可以

### 问题是真实的，而且不是 App 能修的

> 真实反馈：「颜料本身不同颜色的条形码都是一样的，不是每个颜色一个条形码」

这就把这件事说清楚了 —— **条码里根本没有颜色信息**。
同一个品牌、同一批的不同颜色，管子上的条码印的是同一个。
（管子上那张二维码更甚，通常是品牌公众号码，整个品牌所有产品共用一张。）

所以「扫一下就知道是什么颜色」这条路在物理上就不存在。
管子上真正每支都不一样的，是**印上去的字**：群青、钛白、深红。

### 所以默认改成「认字」

扫码页顶部有两个模式，**默认是「认字」**：

| 模式 | 干什么 | 什么时候用 |
|---|---|---|
| **认字**（默认） | Vision OCR 读中文颜色名，匹配颜色库与 42 色预设 | 你那盒颜料的情况 |
| 扫码 | 二维码 / EAN-13 等一维码 | 万一你手上那盒是每个颜色一个码 |

认字的实时流程：镜头对准管子上的颜色名 → 屏幕上跳出

```
┌──────────────────────────────────┐
│ [色块]  群青  PB29                │
│         颜色库里就有，装在 F5 格   │
│         ✓ 可以直接入库      92%   │
│  [ 就是它 ]        [ 重读 ]      │
└──────────────────────────────────┘
```

点「就是它」→ 如果那个颜色已经装在某一格，**直接打开那一格的编辑页**，
改余量、登记补充装库存，一站到位。不用自己回 42 格里找。

### 认字能认出什么

`PaintLabelParser`（纯 Foundation，`scripts/run-label-tests.sh` 有 40 个用例）会从
OCR 的一堆行里推断：

| 读到的 | 处理 |
|---|---|
| 中文颜色名「群青」 | 匹配颜色库 / 预设 → 落到 `PRESET-35` |
| 带「色」后缀「深红色」 | 认成「深红」 |
| 名字混在整行里「马利 群青 5ml」 | 挑出来 |
| OCR 漏字「群」 | 猜「群青」但标为**需要确认** |
| 颜料标准号 `PW6` / `P.B.29` / `PR 106` | 按 Colour Index 号匹配，比认字更硬 |
| 色号 `NO.35` / `#108` / `M-35` / EAN-13 | 填进编号 |
| 品牌「马利」「温莎牛顿」… | 填进品牌 |
| 库里没有的颜色「孔雀绿」 | 建议新建一条，色号 `OCR-孔雀绿` |

防假阳性是刻意做重的：`HAPPY2024` 里**不会**切出 `PY202` 这种假标准号，
`PW06` 也不算合法写法。宁可少认，不可认错。

### 顺带修掉的一个致命阻塞

原来扫到已存在的码会直接 `return`，界面只说一句"已经在颜色库里了"。
配上"不同颜色共用条码"这个现实，后果就是：
**扫完第一支之后，同一盒里别的颜色永远进不来。**

现在改成两条出路：

1. 弹一个解释面板，说清"条码被共用了"，并列出这个码现在挂在哪些颜色上
2. 给出路：「改用认字」或「我知道是什么颜色，手动建一条」

手动建的那条**用颜色名当色号**（`NAME-群青`），而不是用条码 ——
这样同一批里每个颜色各有一条，不会互相顶掉。
而且如果颜色库里已经有同名颜色（比如预设的「群青」），**直接复用它**，
不会建出两个重名的「群青」。

### OCR 的边界

- **完全在本机**跑（Vision），不联网、不上传、不需要额外权限
- 中文 OCR 一帧几百毫秒，所以限流到约每秒一帧，并**要求连续两次读到同一个名字**
  才显示 —— 否则屏幕上的字会一直跳
- 卡片下面有个「看它到底读到了什么」：把 OCR 的每一行原文和置信度摊开给你看，
  "为什么没认出来"是看得见的
- ⚠️ **真机没验证过**：我没有 iPad 可以实测取景与识别率。
  如果中文死活认不出来，第一个要看的是 `QRScannerViewController` 里
  **送帧连接的旋转**（`videoRotationAngle`）—— 画面躺着的话，中文一行都读不出来。
  如果字认出来了但匹配总是错的，那是 `PaintLabelParser` 的阈值问题，把
  「看它到底读到了什么」的截图给我就行。

## 3.13 教材：搜索 / 下载 / 离线阅读

### 它是从哪来的

前身是一份在 iPad 上跑的 **a-Shell Python 脚本**（`main.py`）：登录某个美术教材平台 →
搜索 → 取页 → 8 线程下原图，或者生成一份 HTML 阅读器 + 起一个本地 HTTP 服务丢给 Safari。
功能是通的，但在 iPad 上效果不好。搬进原生 App 时**逐条修掉了那些限制**：

| 原脚本的问题 | 现在 |
|---|---|
| a-Shell 一进后台就被 iOS 挂起 → 本地服务器断 → Safari 里翻页失败 | **没有任何服务器**，页面在 App 内直接渲染 |
| 图片全走远程 CDN，无本地缓存 → 离线不可读、翻页看网速 | 本地文件优先，缺页才走网络并顺手落盘；读过一遍就离线可看 |
| 视口写了 `user-scalable=no`，**双指缩放被浏览器禁用**（提示却写着"支持双指缩放"） | 真的能双指缩放，双击还能放到 2.5 倍 |
| 记不住读到第几页 | 每翻一页写进数据库，"继续阅读"直接回到那一页 |
| 8 线程全速冲，失败只打印一行，哪几页失败无从查起 | 4 路并发 + **每页有状态**，失败页可以单独重试 |
| 进度把失败页算进完成 → "100%" 里可能混着 30 页失败 | 分子只算成功页（这条有 4 个用例专门钉着） |
| token 明文写在 `dxart_token.txt` | **Keychain**，不进备份，可一键退出登录 |
| `TCPServer(("", 5000))` 绑定 `0.0.0.0` → 同 WiFi 的人能翻你整本教材 | 没有服务器，不存在这个问题 |
| `int(page_num)`、`data["data"]["chapterList"]` → 页码是字符串/null 就崩 | 宽松解析 + 每个可疑点都有测试 |
| 书名为目录名，**不截断** → 中文书名超 255 字节写不进去 | 按 UTF-8 字节安全截断，目录名带书 id（防同名互相覆盖） |
| 完全用不上 Apple Pencil | 见下一节 |

### 用法

侧边栏「教材」→「找教材」搜书名 → 「加入」→ 详情页里：

- **直接读**：在线阅读，读过的页自动留在本地
- **下载整本**：有进度、能暂停、能只重试失败的那几页
- 「每页状态」网格让你看得见每一页是已完成 / 失败 / 待下载

### 关于下载：一句实话

下载是**前台会话 + 断点续传**，不是 `URLSessionConfiguration.background`。
下载期间会禁止息屏，切后台时会申请一小段额外时间。
被系统挂起后任务停在磁盘状态里，回来点「继续下载」接着下 —— 不会白下。

没做真正的后台下载，是因为我**没法在真机上验证**后台会话那套
（delegate 生命周期、被系统回收后恢复、`handleEventsForBackgroundURLSession` 接线），
而它的失败方式很隐蔽：看起来在跑，其实早停了。宁可给你一个行为可预期的实现。

### 接口的一处自由度

域名、`version` 头、`appVersion` 参数都是从厂家客户端逆向出来的**实测值**。
厂家一升级 App 就可能失效 —— 所以设置里留了「接口设置」可以自己改，
不用等重新打包。

**只有版本号这类会被厂家单方面提升的值允许改。** 接口路径、参数名、
请求头一律写死：那是契约，改了就真错了。

## 3.14 Apple Pencil 批注

### 一条设计原则：笔用来画，手指用来翻页

`PKCanvasView` 的 `drawingPolicy = .pencilOnly`：

- **笔**：圈重点、画结构线、在参考图上描
- **手指**：翻页、缩放、呼出菜单

这是阅读器唯一说得通的交互 —— 美术生一手拿笔圈画，另一只手的拇指翻页。
如果手指也能画，就没法翻页；如果笔也能翻页，就没法画。

这条**故意不跟随系统的「只使用 Apple Pencil 绘图」开关**：
那个开关是给绘画 App 的，阅读器必须一直是 pencilOnly，
否则手指一拖就在教材上留一道线。界面上会跟用户说明这一点。

批注模式下画布会吞掉手指拖动，所以翻页改用两个滑动手势
（`UISwipeGestureRecognizer`）—— 滑动和"用笔画一笔"在触摸类型上就是两回事，
不会互相干扰。

### 为什么用 PencilKit 而不是自己画线

自己用 `Canvas` + `DragGesture` 画线会丢掉笔的全部价值：

| 丢掉的东西 | 后果 |
|---|---|
| 压感与倾斜 | 圈重点、画结构线的手感完全不对 |
| 系统级预测与合成 | 延迟高一个数量级，写起来像在拖绳子 |
| 防误触 | 手掌按在屏幕上会留痕 |
| 撤销/重做栈、橡皮 | 全部要自己实现 |

这三样正是"适配 Apple Pencil"的全部意义。自己实现等于没适配。

### 双击笔身 / 捏合笔身

`onPencilDoubleTap` 与 `onPencilSqueeze` 是 **iOS 17.5+** 的 API
（本工程最低 17.0），所以包在 `#available` 里 —— 17.0–17.4 上屏上的批注按钮仍然可用。

做什么**由用户在系统设置里的绑定决定**：

| 系统里绑的动作 | 阅读器怎么做 |
|---|---|
| 切换橡皮 | 进入批注并切到橡皮 |
| 切换上一个工具 | 进入批注并切回细笔 |
| 显示调色盘 / 墨迹属性 | 进入/退出批注 |
| **忽略** | **什么都不做** |

最后一行是刻意的：用户明确关掉了这个手势，我们装作没看见就是 bug。
功能不会因此消失 —— 屏上的批注按钮始终在。

### 批注存在哪

`PKDrawing.dataRepresentation()` 写到 `<书目录>/drawings/0007.drawing`，不塞进数据库：

- 一张批注动辄几十 KB，几百页就是十几 MB，放进 SwiftData 会让每次 fetch 都背着它
- 路径**可推导**，所以页记录里不用加字段，也就没有 schema 迁移
- 删书时跟着目录一起删

空批注（用户清空了）会把文件删掉，而不是留一个空文件 ——
否则"这页有批注"的标记会一直亮着。页面列表里给有批注的页打橙点。

## 3.15 其他耗材：从表单改成卡片

真实反馈：「其他耗材管理要重构，太反人类，应该要和颜料盒一样。
而且单位预设也不太好用」。

原来那一版确实反人类，具体反在哪：

| 原来的做法 | 为什么难受 |
|---|---|
| 改数量要点四次：点行 → 弹表单 → 找「还剩」→ 点数字 → 键盘 → 保存 | 颜料盒那边是**点一下 → 五个大按钮 → 完事** |
| 只有一个数字（"3 张"） | 没有"这是多还是少"的参照；颜料盒有余量条 |
| 纯文字列表 | 一屏看不了几项，也没法扫视 |
| **单位是三选一的菜单** | 想填「毫升」「米」根本没门路 |
| 换分类会**悄悄改掉已填的单位** | 把「米」变成「张」，这条最气人 |

现在：

- **卡片网格**，每张卡一条余量条 —— 跟颜料盒同一套视觉语言
- 点卡片 → **大按钮快调**（用完 / 补满 / 加减 / 滑一下），不用键盘
- 新增「**满量**」字段：设了才有真正的比例，不设也能用（只是没有精确比例）
- 单位**自由输入** + 常用项点选 + 记住用过的；换分类**只补空值，绝不覆盖**
- 快用完的排在各分类最前面
- 余量分五档：用完了 / 快没了 / 剩一半 / 够用 / 充足

档位逻辑（`StockPlan.level`）有个刻意的选择：**没设满量、也没设提醒线时，
只报「够用」，不猜一个「快没了」出来**。猜出来的警告会让用户莫名其妙。

## 3.16 工业喷码：走到哪一步了

真实反馈：「ocr 识别对工业喷码字体识别精度不高，可以尝试用现成的更高级的轻量 ocr 模型」。

### 为什么喷码难认

跟印刷体是两种东西，而 Vision 是按后者训练的：

| 喷码的特点 | 后果 |
|---|---|
| 字是**点拼出来的**（1–4 px 空隙） | 模型看到的是"一堆孤立的点"，不是一个字 |
| **字很小**（管子上那行常只有 1–2 mm） | 一帧 1920×1080 里它可能只占 12 px |
| **明暗不均**（圆柱面 + 反光） | 全局阈值一卡就断成两截 |
| **不是词**（`20250612A3`） | 语言纠正会把它"纠正"成别的 |

### 已经做完的：图像预处理（55 个用例）

`TextImagePreprocessor` 四步，每步冲着一个具体毛病：

```
放大 2–3 倍      → 治"字太小"（双线性插值顺手糊掉一部分缝隙）
对比度均衡       → 治"明暗不均"第一层
局部自适应二值化 → 每个像素跟**自己邻域**均值比，而不是跟整幅图比
形态学闭运算     → 膨胀把点连成线，腐蚀再收回原粗细
```

再加**数码变焦**（只取画面中央、放大后再识别）—— 喷码真正的瓶颈是
**像素密度**，不是模型。界面上是右下角两个开关：「放大」与「喷码」。

还会**自动判断**：开扫第 3 帧时用"笔画里短横段的占比"估一下像不像点阵，
像就自动切到喷码档位并提示一声。用户不用懂这两个模式的区别。

> 写这一块时被合成图测试抓出一个真 bug：**闭运算的极性写反了** ——
> 这个表示法里"墨 = 0、底 = 255"，也就是前景是小的那个值，
> 而标准形态学例子默认"前景 = 1"。照搬过来之后膨胀变成让白长大，
> 把笔画整条擦掉（黑像素 64 → 0）。测试里那条"墨量不减"就是为它加的。

### 已经做完的：换模型的前置逻辑（66 个用例）

「换一个更高级的轻量模型」这条路绕不开三件事，而它们正是整条链上
**最容易错、又最难发现**的地方：

1. **字符表索引约定** —— blank 在 0、字典从 1 开始、空格在末尾，
   所以输出维度是 `6623 + 2 = 6625`。错一位就"全都认出来了但每个字错位一个"。
2. **CTC 解码** —— 被 blank 隔开的重复字是**两个字**：
   `[a, blank, a]` → `aa`，而 `[a, a, blank]` → `a`。
   写成"先去 blank 再去重"就会把前者错解成 `a`。
3. **输入归一化** —— `/255` 再 `(v−0.5)/0.5` 到 −1…1，CHW 排列，高 48、
   宽补到 8 的倍数（骨干网下采样 8 倍）。

这三件事全是纯数学 + 查表，**不需要模型就能测**，所以先测透了。
字符表用的是 PaddleOCR 官方那份 `ppocr_keys_v1.txt`（6623 字，已入库并打进 App）。

### 拿真照片验证后的发现（你拍的青竹补充装）

两张 iPhone 原图（4032×3024，EXIF orientation = 6）跑出来的结论：

| 发现 | 对 App 的影响 |
|---|---|
| 批号 `2026060720301450A4` 是**竖排**的（沿袋子纵向印） | 必须先转正 → 加了「转正」按钮（0°/90°/270°，交给 Vision 的 `CGImagePropertyOrientation`，不自己写旋转矩阵） |
| 字符高约 **30–45 px**（12 MP 原图） | 尺寸够用，瓶颈不是像素密度 —— 原来那套"裁中央再放大"的假设是错的 |
| 喷码**不在画面正中**（人本能地把整包对进取景框） | 「放大」裁中央会把要认的那行裁掉 → 改成**在画面上点一下，只识别那块**（再点框内取消） |
| 圆柱面有一条**高光带**横穿字 | 局部自适应二值化正是冲这个来的，保留 |
| 点阵笔画之间有 1–4 px 空隙 | 闭运算把点连成线，保留 |

这四条里前三条是**真照片才暴露出来的**，之前靠推理没想到。
尤其"裁中央"那条 —— 我原来的设计看起来合理，实际正好会切掉目标。

## 3.17 Apple Watch 端（保湿计时 + 采购清单）

手表上只放两件事，而且都是**在表上能独立成立**的：

| 功能 | 为什么适合放在手腕上 |
|---|---|
| **保湿计时** | 这件事的本质就是"过一会儿提醒我"，而提醒最该出现在手腕上（手腕会震，手机在包里不会） |
| **采购清单** | 在画材店里一只手拿东西、另一只手划清单 —— 掏 iPad 不现实 |

### 和 iPad 是同一套模型，不是抄一份

`DryingModel.swift` 与 `WetnessPreferences.swift` 都是纯 Foundation 的，
手表 target **直接编译同一份源码**（见 `project.yml` 里 ArtAssistWatch 的 sources）。
所以两边算出来的补水时间一定一致，不会出现"手表说 12 分钟、iPad 说 20 分钟"。

### 刻意**没有**做的：看颜料盒余量 / 在途包裹

因为搬数据这条路在当前的交付方式下走不通：

- 跨设备共享数据通常用 App Group 或 iCloud —— 本项目**刻意不使用任何 entitlement**
  （免费 Apple ID 签不了，见 `project.yml` 里的说明）；
- 另一条路是 WatchConnectivity，但它要求**配对的 iPhone** ——
  而这个 App 实际装在 **iPad** 上，iPad 根本不支持 `WCSession`。

所以与其在表上摆一份和 iPad 对不上的假数据，不如只做能独立成立的功能。
手表上的两个功能各自一份 UserDefaults，完全离线可用。

### 手表上没有天气，所以温湿度是手调的

用数字表冠调温度和湿度（默认 25℃ / 50%），界面上一直显示当前用的是哪两个数 ——
因为预测值只在它们准确时才有意义。不想管的话，也可以直接点 10 / 15 / 20 / 30 分钟。

### 工程上的两个注意点

1. **手表 App 必须嵌进 iOS App**（`Watch/ArtAssistWatch.app`），
   bundle id 必须是宿主的前缀（`com.yuanjunhao.artstock.watchkitapp`），
   否则安装时报"watch app's bundle identifier is not prefixed by …"。
   验证脚本里有一条断言专门盯这个嵌入关系。
2. ⚠️ **构建时不能再写 `-sdk iphoneos`**。命令行上的 `-sdk` 是全局覆盖，
   会把手表 target 也按 iOS SDK 编译，于是 `import WatchKit` 直接报
   `Unable to resolve module dependency: 'WatchKit'`。
   只给 `-destination 'generic/platform=iOS'`，Xcode 会按每个 target 的
   platform 分派 SDK。`scripts/make-unsigned-ipa.sh` 与 `scripts/verify-all.sh`
   都已按这个改过（代码里有注释说明，别再"顺手"加回去）。

## 6. 扫码能扫到什么（现实预期）

**这一点必须说清楚，否则会失望**：颜料管上印的多半是 **EAN-13 零售条码**，
那串数字**不携带任何颜色信息** —— 它只是厂家的商品编号。

所以流程设计成「扫到多少算多少」：

| 扫到的东西 | 能得到什么 |
|---|---|
| 二维码 / JSON 载荷 | 颜色名 + 色值自动填好，**直接入库** |
| URL 参数（`?name=群青&hex=%232E5BFF`） | 从参数里提取 |
| 键值文本（`编号=PH-001` / `颜色名：酞菁蓝`） | 从中英文键提取 |
| **零售条码（最常见）** | **只有编号** —— 颜色由你选 |

界面上会明确告诉用户属于哪一种，不让人误以为扫一下什么都有了。

支持解析五种载荷形态（优先级从高到低）：JSON → URL → GS1 → 键值文本 → 纯文本。
中文键做了宽松匹配（`颜色名` / `颜色` / `色名` / `色彩名` 都认），
中文色名也能自动映射到色值（"群青" → `#2E5BFF`）。
解析器有 **67 个用例**覆盖（`scripts/run-scan-tests.sh`）。

3. **颜色库有一份 42 色水粉预设**（见第 3.6 节），但色值是**按色名推断的近似值**，
   不是厂家官方色值。其他体系（油画、丙烯）没有内置色卡。

5. **`xcode-select` 没有指向 Xcode**（仍是 CommandLineTools）。
   不影响 Xcode GUI，但命令行需要 `export DEVELOPER_DIR=...` 或
   `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`。

6. **本机 8 GB 内存**跑 Xcode 比较吃力，建议关掉模拟器、直接用真机调试。

7. **GitHub Actions 工作流未实际跑过**。本机已能本地出包，CI 属于备用路径。
